AI / ML Architecture

An honest, code-accurate description of what the LSTM, the GNN, and the deterministic Risk Engine each actually do — and, just as importantly, what they don't.

LSTM and GNN are two independent advisory signals, not a fusion model. Neither one ever writes to Zone.current_count or a risk score — they only return numbers the API hands back as clearly-labeled advisory fields (/api/ai/forecast/{zone_id}, /api/ai/network-pressure). The Risk Engine's 5-factor deterministic formula (risk_factors() in engine.py) is unchanged by either of them, and every recommended action still requires explicit operator approval before it changes anything.

1. LSTM — "What will happen?"

Real, trained model

A trained PyTorch model. Not a placeholder, not a formula dressed up as ML.

Architecture
One shared-weight nn.LSTM (hidden_dim=64, 1 layer) across every zone/domain, with 3 separate linear output heads for the three horizons — a direct multi-horizon prediction, not a recursive rollout.
Input window
The last 12 ticks (t-11 … t) of that zone's own CrowdSnapshot history.
Prediction horizons
+15m, +30m, +60m occupancy %, output simultaneously by 3 heads off the same final hidden state.
Feeds from live data
Every new CrowdSnapshot (from any source — camera, check-in, manual, simulation) slides the input window forward by one tick the next time a forecast is requested.

39 real input features per tick: occupancy %, entry-rate %, exit-rate % · event phase (one-hot) · event type (one-hot) · zone domain — venue/transport/hospitality (one-hot) · sport / competition / tournament gender / stage (one-hot, sports events only) · has-ticket-data flag · sell-through % · booking velocity · demand intensity · log-scaled capacity · ticks-since-phase-start. Deliberately excluded: scenario label, team identity, and zone-role identity — the guardrails that stop it from memorizing one seeded layout instead of generalizing.

Works for any zone in any event — verified live against this event's own zones, not just the original seeded demo layout.

2. GNN — "Where will pressure spread?"

Real, trained modelLimited scope

A hand-rolled inductive graph network in plain PyTorch (no torch_geometric) — real message passing, with an honest limitation.

Nodes
Zones — but a fixed, hardcoded set of 9 illustrative zone roles (gate/concourse/station/hotel-style) baked into the training graph, not read from this event's own Zone/ZoneEdge rows.
Edges
11 hardcoded walkway connections with per-edge propagation lag (default 1 tick, up to 5 for the longer gate↔station links).
Node features
Occupancy %, entry-rate %, exit-rate %, zone domain (one-hot) — 6 dims.
Prediction target
Next-tick occupancy % per node, propagated from each neighbor's own lagged telemetry — roughly a 1-minute-ahead spatial expectation, not a multi-horizon forecast like the LSTM.

Honest limitation: because the graph's 9 node roles are matched by exact zone name, the GNN signal is only available for an event whose zones happen to use those seeded demo names. Any operator-renamed or custom event — including this platform's own live custom events — gets {"available": false, "reason": "…"} from /api/ai/network-pressure, by design, rather than a guessed number. This is a real, verified behavior of the current build, not a hypothetical caveat.

3. Fusion

Does not exist

There is no trained fusion neural network combining the LSTM and GNN. The two are surfaced as separate, independently-labeled advisory fields. The one place the code even attempts to feed the LSTM's forecast into the GNN's own-occupancy input channel is an offline evaluation script — never the live inference path the app actually calls, which always runs the GNN on current telemetry alone. That offline experiment found composing the two signals had no measurable benefit, which is why the live system keeps them independent rather than presenting an invented "AI fusion score."

This is correctly called an advisory architecture (or model ensemble of two independent signals), not a fusion model — and the Risk Engine, not either ML model, remains the authoritative decision layer for risk levels, alerts, and evacuation guidance.

4. Update behavior — training vs. inference vs. live telemetry

  • Training happens offline, ahead of time, on a synthetic generative dataset built to cover many crowd-dynamics scenarios — not on this event's real history. This produces the saved model weights the app loads at startup.
  • Inference happens on demand: each time an attendee or operator requests a forecast, the current 12-tick window (or current graph snapshot) is fed through the already-trained weights.
  • Live telemetry — a new camera count, check-in, manual entry, or simulation tick — updates the input those next inference calls will see.

Live data updates the inference input; model weights are not retrained online.

What stays authoritative

  • The deterministic 5-factor Risk Engine (risk_factors()) computes every zone's risk level and every alert — unchanged by either ML model.
  • Neither model ever mutates Zone.current_count, a risk score, or an alert directly.
  • Every recommended action still requires explicit operator approval before it changes any live state.
  • Where a model's output isn't available or reliable enough (not enough history, unmatched zone graph), the API returns available: false with a stated reason — never a guessed number.
